================================================================================
一、CSS 布局类
================================================================================

[1] 元素被「裁掉」，算出来的尺寸和看到的完全不一样
--------------------------------------------------------------------------------
  现象：JS 把面板高度算成 525px，getBoundingClientRect 也返回 525，
        但屏幕上只显示 90px，而且屏幕越矮裁得越狠。
  根因：面板是 position: absolute，挂在某容器里；
        那个容器的祖先（这里是 #top）设了 overflow: hidden，
        超出祖先边界的部分直接被裁。
  正确：需要「盖住整页」的浮层（下拉、弹幕、面板）一律用 position: fixed，
        基准是视口，谁也别想裁它。代价是不跟随滚动，页面不滚动时可接受。

[2] 用 vh 当元素高度是错的
--------------------------------------------------------------------------------
  现象：搜索候选框写 height: 58vh，窄屏高屏都别扭，改一次骂一次。
  根因：vh 是「视口高度的百分比」，和元素的实际起点毫无关系。
        起点由上方内容（标题区）撑开，会变；58vh 不会变。
        于是起点下移时溢出、上移时留一大片空。
  正确：高度 = 终点 − 起点，两个都要实算。
        起点用 getBoundingClientRect().bottom，终点用 window.innerHeight。
        JS 里算好写成内联 style，CSS 不要写 height。

[3] #id 的优先级能压掉 html[attr] .class
--------------------------------------------------------------------------------
  现象：写了 html[data-theme="c"] main { display: flex }，不生效。
  根因：那个元素是 <main id="top">，别处有 #top { display: block }。
        #id = (1,0,0)，html[attr] .class = (0,2,1)，前者赢。
  正确：改带 id 的元素，选择器里就写上 #id，或者干脆用 !important 兜底。

[4] 裸类名压不过带属性前缀的规则
--------------------------------------------------------------------------------
  现象：mobile.css 里写 .hb-row { flex-direction: column }，
        即使它后加载，手机上还是横排。
  根因：skin-c.css 里是 html[data-theme="c"] .hb-row（0,2,1），
        mobile.css 里是 .hb-row（0,1,0）。特异性输了，后加载也没用。
  正确：两端规则的前缀保持一致（都用 html[data-theme="c"] 开头），
        再靠加载顺序决定胜负。

[5] left: 0 + right: 0 会让 width 失效
--------------------------------------------------------------------------------
  现象：写了 width: 600px，面板宽度却是 335px。
  根因：同时写了 left: 0 和 right: 0 —— 左右都贴边时，
        宽度由容器决定，width 根本不参与计算。
  正确：要么 left + width + right: auto，要么 left + right（不写 width）。

[6] margin: auto 和 flex: 1 一起用会打架
--------------------------------------------------------------------------------
  现象：想让它居中又占满，结果跑到别的元素上面去了。
  根因：flex 布局里 margin: auto 会抢占剩余空间，
        和 flex-grow 的计算互相干扰。
  正确：二选一。要居中用 justify-content / align-items；
        要占满用 flex: 1，不要加 auto 外边距。

[7] flex: 1 1 0 配 min-width: 0 会把元素压成 0 宽
--------------------------------------------------------------------------------
  现象：标题区整块消失，加红色 outline 只看到 3px 宽的一条线。
  根因：flex-basis 是 0，min-width 又是 0，兄弟元素一挤它就归零。
        里面的文字溢出了容器，被挡住看不见。
  正确：flex-basis 用 auto，再给一个 min-width（如 300px），
        或者直接用 clamp() 限制宽度范围。

[7b] flex 填充链断在中间某一层
--------------------------------------------------------------------------------
  现象：#top 有 683 高，.pw-row 写了 flex: 1 却算出高度 0，
        三个入口靠 min-height 撑着，下面空了一大片。
  根因：.pw-row 不是 #top 的直接子元素 —— 它和 .hero-block 一起
        被包在 <div class="home-top"> 里。而 .home-top 是「按内容高」的，
        所以 .pw-row 的 flex: 1 没有高度可分配。
  正确：填充链要一环一环补全：
          #top(Fill) → .home-top(Fill) → .pw-row(Fill) → .pw(各自 Fill)
        少中间任何一环，下面所有的 flex: 1 都是空的。
  排查：先打 console.log(el.parentElement.id + '/' + el.parentElement.className)，
        别假设 DOM 层级「应该是」什么样。这个项目里
        .hero-block 和 .pw-row 都包在 .home-top 里，很容易漏掉。

[8] column 布局 + flex-wrap: wrap 会「横着铺开」
--------------------------------------------------------------------------------
  现象：容器明明是 flex-direction: column，子元素却排成一行。
  根因：带了 flex-wrap: wrap。竖排放不下时会「换列」，
        视觉上就是横向铺开，很容易误判成 direction 没生效。
  正确：竖排容器确认 flex-wrap: nowrap。

[9] display: block 下 order 无效
--------------------------------------------------------------------------------
  现象：设了 order: 3，元素位置没变。
  根因：order 只对 flex / grid 子项生效。
  正确：父容器先 display: flex（或 grid），再谈 order。

[10] 只改 display 没改 flex-direction
--------------------------------------------------------------------------------
  现象：把卡片改成横向布局，箭头还是掉到下一行。
  根因：容器原本是 flex-direction: column，只写 display: flex 不改变方向。
  正确：display 和 flex-direction 一起写。

[11] ::after 同时承担「画内容」和「当覆盖层」会互相顶掉
--------------------------------------------------------------------------------
  现象：加了整块点击的覆盖层，箭头图标直接消失。
  根因：两条规则都写在 ::after 上，后一条把前一条的 content 覆盖了。
  正确：内容用 ::after，覆盖层用 ::before（或反过来），一个伪元素只干一件事。

[12] 绝对定位元素改了定位方式，别忘了一起改 top/right/bottom
--------------------------------------------------------------------------------
  现象：天气块压住搜索框，两个元素重叠。
  根因：原样式是 position: absolute + top/right/bottom（挂在角落），
        后来改成普通 flex 子项，但只改了 flex，没把 position 改回 static。
        它仍然浮在上面。
  正确：改定位方式时，position 和 top/right/bottom/transform 一起处理干净。

[13] 变量名撞车
--------------------------------------------------------------------------------
  现象：首页大卡的渐变背景不显示，或者宽度算错。
  根因：自定义属性 --hero-rail 原本是「右角按钮占的宽度 200px」，
        拿来当渐变颜色用了，两边互相覆盖。
  正确：新增变量前先全文件搜一遍同名。语义不同的分两个名字
        （--hero-rail 宽度 / --hero-rail-bg 背景）。


================================================================================
二、JS / DOM 类
================================================================================

[20] display: none 时 getBoundingClientRect 全返回 0
--------------------------------------------------------------------------------
  现象：面板显示出来高度不对，或者算出负数。
  根因：元素隐藏时没有任何布局，rect 全是 0。
        先设 hidden = false 再量，顺序反了。
  正确：先让它可见，同一个调用栈里再量（同步重排，能拿到正确值）。

[21] CSS 覆盖了 HTML 里的 placeholder
--------------------------------------------------------------------------------
  现象：改了 HTML 的 placeholder，页面没变化。
  根因：app.js 里有一行 input.placeholder = '...' 硬编码，
        加载时把 HTML 的值冲掉了。
  正确：文案只有一处真相。要么在 HTML，要么在 JS，别两边都写。

[22] 绝对定位的浮层挂在 header 里，被层叠上下文限制
--------------------------------------------------------------------------------
  现象：面板 z-index 设到 9999 还是被顶栏盖住。
  根因：祖先有 transform / filter / opacity < 1 会创建新的层叠上下文，
        子元素的 z-index 只在那个上下文内比较。
  正确：这类浮层用 insertAdjacentHTML 直接挂到 body 上。

[23] 探针脚本自己有 bug，导致误判
--------------------------------------------------------------------------------
  现象：测出来某个功能坏了，实际是好的。
  根因：探针里写错了选择器、时序太早、或者用了不存在的属性。
  正确：探针也要当代码审一遍。拿不准就 printf 中间变量，
        不要只看最终结论就下判断。


================================================================================
三、验证 / 测试环境类
================================================================================

[30] Chrome headless 的窗口有最小宽度
--------------------------------------------------------------------------------
  现象：设 --window-size=390,844 截图，页面右边被裁，以为布局溢出。
  根因：headless 的最小窗口宽是 500。实际按 500 渲染，390 的图是从中裁出来的。
  正确：验证手机端至少用 500 宽。要看更窄的，用 DevTools 设备模拟。
        判断「有没有横向溢出」用 scrollWidth > innerWidth，不要看截图。

[31] dump-dom 和 screenshot 的视口高度不一致
--------------------------------------------------------------------------------
  现象：dump-dom 报视口 369，截图里内容却到 500。
  根因：两种模式对 --window-size 的解释不同（截图不含浏览器 UI）。
  正确：判断布局用 dump-dom 的数据，看视觉效果用截图，两者不要混着推理。

[32] 截图 / 脚本有缓存
--------------------------------------------------------------------------------
  现象：改了 CSS，截图没变化，以为没生效。
  根因：浏览器缓存了带 ?v= 的旧资源，或者用了复用的 user-data-dir。
  正确：每次截图用新的 --user-data-dir；
        改完静态资源顺手升 ?v= 版本号。

[32b] requestAnimationFrame 在无头浏览器里可能不回调
--------------------------------------------------------------------------------
  现象：收藏栏「溢出才显示更多按钮」的逻辑，截图里是好的，
        探针跑 dump-dom 时一直判定成「没溢出」，永远不显示。
  根因：headless + --virtual-time-budget 下，rAF 的回调不一定被调度。
        页面看起来渲染了，但那一帧的回调没执行。
  正确：需要「等布局稳定后再量」的地方，用 setTimeout(fn, 32) 而不是 rAF。
        32ms 足够浏览器算完布局，肉眼也看不出延迟，而且在虚拟时钟下会正常执行。

[33] IntersectionObserver 在虚拟时钟下不回调
--------------------------------------------------------------------------------
  现象：懒加载逻辑在自动化测试里永远不触发。
  根因：headless + --virtual-time-budget 下 IO 的回调不执行。
  正确：这类逻辑没法在 CI 里验证，说明清楚，靠真机确认。

[34] 截图窗口尺寸随手设，和用户真实环境对不上
--------------------------------------------------------------------------------
  现象：我用 --window-size=1080,520 截图，看到候选框 285 高；
        用户那边实测 708×148。两边数据差 5 倍，来回几轮都在讨论
        「为什么不一样」，甚至怀疑算法本身写错了。
  根因：headless 的窗口尺寸是我自己随手设的，和用户的真实视口毫无关系。
        · 用户屏幕是 1920×1080
        · 但去掉任务栏（约 40）+ 浏览器地址栏/书签栏（约 120）
        · 网页实际可用只有 **1920 × 918**
        我拿 1080×520 的截图去论证 1920 宽屏下的表现，结论必然是错的。
  正确：
    1. 验证视觉之前，先问用户「你网页实际能用的可见区域是多少像素」
    2. 默认按 1920 × 918 验证（不是 1080）
    3. 不要用自己临时设的尺寸去下判断；要测极端情况就明说「这是压测，
       不是你的实际环境」

[35] 拿 dump-dom 和 screenshot 的数据混着推理
--------------------------------------------------------------------------------
  现象：dump-dom 报视口 369，截图里内容却到 500，两个数字对不上，
        于是怀疑 getBoundingClientRect 算错了。
  根因：两种模式对 --window-size 的解释不同（截图不含浏览器 UI，
        dump-dom 会扣掉一截）。同一个命令参数，两种结果。
  正确：布局数值用 dump-dom，视觉效果用截图，两套数据不要交叉推理。
        要对比就用同一模式、同一尺寸跑两次。


================================================================================
四、命令 / 工具类（Windows PowerShell）
================================================================================

[40] 引号和括号被 PowerShell 吃掉
--------------------------------------------------------------------------------
  现象：注入的 JS 里字符串变成空，或者整条命令解析失败。
  根因：PowerShell 对 @' '@ 和双引号里的 $ 有自己的一套规则。
  正确：复杂脚本写成 .js / .html 文件再执行，不要在命令行里拼。

[41] 读写同一文件时编码不一致会损坏内容
--------------------------------------------------------------------------------
  现象：命令被安全拦截，或者文件变成乱码。
  根因：Get-Content 和 Set-Content 用了不同编码。
  正确：读写都显式写 -Encoding UTF8 -NoNewline；
        或者改用文件编辑工具，别用 shell 做文本替换。

[42] 数组被当成字符串
--------------------------------------------------------------------------------
  现象：测试参数变成 "5x0"、"9x0"，窗口尺寸成了 5×0。
  根因：@(@('500','900')) 多包了一层，$s 变成单元素数组，
        $s[0] 取到字符 '5'。
  正确：foreach 里用 @('500','900') 直接遍历，或者显式写 $s[0], $s[1]。
        发现参数诡异时先怀疑这一条。

[43] CRLF 让多行字符串替换失败
--------------------------------------------------------------------------------
  现象：replace 的锚点「明明一样」却匹配不上。
  根因：文件是 CRLF，脚本里拼的字符串是 LF。
  正确：拼接时用 $nl = 文件里的换行符；或者按行号 / 正则处理。


================================================================================
五、流程类（最容易犯）
================================================================================

[50] 改一端顺手把另一端带崩
--------------------------------------------------------------------------------
  现象：用户只说改电脑端，手机端布局跟着变形。
  根因：两端规则写在同一批选择器里，或者共享了同一个 CSS 文件。
  正确：桌面 css/skin-c.css，手机 css/mobile.css，各改各的。
        改完两端分别验证一次。这是本项目最高频的事故。

[51] 反复追加覆盖，最后谁也搞不清哪条生效
--------------------------------------------------------------------------------
  现象：同一个元素被 10 条规则提到，改一处坏一处。
  根因：遇到问题就往下 append 一段覆盖，累积到 1400 行。
  正确：同一元素被覆盖超过 3 次，就停下来重写这一段，
        只保留最终生效的那一份。

[52] 用「我以为」代替「量一下」
--------------------------------------------------------------------------------
  现象：连续几轮都在修同一个问题，每次猜一个原因。
  根因：没量就改。改完也没验证具体数值，只看截图够不够大。
  正确：先写探针，把实际数值打出来（宽、高、top、bottom、computed style、
        内联 style），确认根因再动手。这轮排查「候选框太矮」就是靠
        一次探针发现「内联 525 / 实测 525 / 视觉 90」，才定位到 overflow 裁剪。

[53] 截图看着没问题就以为通过了
--------------------------------------------------------------------------------
  现象：截图里正常，用户那边是坏的。
  根因：截图用的是特定窗口尺寸，覆盖不到用户的实际情况。
  正确：至少测三档：矮窗口（520）、常规（900）、手机（500）。

[55] 别写「介绍页面布局」的废话
--------------------------------------------------------------------------------
  现象：页面上出现这几类文字，用户每次都要求删掉 ——
        · 「左边选预设，中间改正文，右边直接去 AI 对话」   ← 在描述布局
        · 「这里放的是全部预设，翻译只是其中一项」         ← 在描述结构
        · 「所有提示词都配同一批 AI 对话入口 —— 就在右边那一列」 ← 在指路
        · 「完整工具 · 就在这一页」                        ← 纯废话
  根因：这些话讲的是「页面长什么样」，用户看一眼就知道，写出来只是噪音。
        尤其做成分层布局（手机一页一屏、或者改版）之后，这些指路的话
        会直接变成错的 —— 右边根本没有那一列了。
  正确：描述只写两件事 ——
        ① 这东西为什么好用（价值、原理、比替代方案强在哪）
        ② 用户要怎么用才能拿到结果（操作步骤，不是页面布局）
        不写：布局说明、元素位置、数量统计、「就在这里」「就在那一列」。

[56] 页面标题按「功能」起，不要按「流程第几步」起
--------------------------------------------------------------------------------
  现象：预设页拆成三层之后，大标题还叫「提示词预设」，
        到第三层（AI 入口）就明显不合适了。
  正确：标题按整块功能命名，所有层通用。比如整块叫「提示词」，
        第 1 层选场景、第 2 层看结果、第 3 层去 AI，都能挂在「提示词」下面。
        同理：改名要看「这个东西本质是什么」，不是它原来叫什么。

[57] 加工具之前先想清楚「浏览器能不能拿到这个数据」
--------------------------------------------------------------------------------
  现象：用户提到某个桌面软件的功能（显卡驱动的性能叠加层），
        第一反应是「在网页里也做一个」，结果做不出来。
  根因：浏览器有沙箱限制。GPU 占用率、GPU 温度、显存用量、
        CPU 具体型号、硬盘容量 —— 这些网页一律读不到，
        不是技术难度问题，是浏览器故意不给。
  正确：先分清三档 ——
        · 能拿到：FPS（自己算）、视口尺寸、CPU 核心数、内存档位、网络类型、显卡型号
        · 拿不到：GPU 占用 / 温度 / 显存、CPU 型号、硬盘、主板
        · 更好的做法：教用户用系统自带的工具，而不是自己造个残缺版
          （任务管理器、dxdiag、msinfo32、显卡驱动的叠加层）
        判断标准：如果用户真正想要的是「在打游戏时实时看」，
        那我们网页里做什么都没用 —— 网页是前台应用，游戏在后台全屏。
        这时候正确的事情是「教」，不是「做」。
